# Getting help

There's one maintainer here, so the fastest route depends on what you've actually got.

**Something is broken** — open an issue on that repo. The bug forms ask for the OS, the app
version and the machine because those three answers decide whether a report is reproducible or a
dead end. A crash pasted as text is worth more than a screenshot of it.

**Something the app did to your machine and didn't undo** — file it as a bug straight away rather
than working out whether it's "really" a bug first. Several repos have a dedicated form for this
class of thing (deleted the wrong file, left hardware disabled, changed a setting and didn't put
it back) and it jumps the queue.

**A question, or you're not sure it's a bug** — Discussions on the repo, or a blank issue. Blank
issues are deliberately left enabled everywhere. A report filed in the wrong shape is much better
than one that never gets filed.

**You want the tool to do something new** — the feature form. It asks what problem you have rather
than what feature you want, and that isn't a formality: these tools are free with no paid tier and
deliberately small, so the argument that works is that something costs you real time.

**You found a vulnerability** — [SECURITY.md](SECURITY.md). Not a public issue.

**Hardware I don't own** — reports are still welcome, and genuinely useful. Say up front which
machine, GPU or peripheral you're on. A "this doesn't work on X" that I can't reproduce is still
worth having on record, because the next person on X will find it.

## What to expect

Best effort, in evenings and weekends. Data-loss and security reports get looked at first,
then bugs, then features. If something's been sitting untouched for a couple of weeks, a nudge on
the thread is welcome rather than rude.
